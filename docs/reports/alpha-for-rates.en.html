Using alpha for PV, par rates and risk on the Rates page

Whether qube's Rates page (the one-line IRS and CCS pricer) can use alpha's curve building and flow-table valuation, and a proposal. 2026-11-17. Every figure is synthetic. 日本語

Answer: yes. Not by wiring today's alpha in as it is, though: add one entry to alpha for deterministic (no Monte Carlo) rates valuation, and call it from qube as a persistent worker in a separate process.

  • With alpha's pieces (curve building, interpolation, the flow table's approach, the par-delta Jacobian), a 10-year JPY swap takes 12 µs for PV, par rate and zero delta on every node. The gradient matched a bump to two decimals.
  • The cost is on the curve side. Alpha's reference bootstrap takes 1.8 ms for the two JPY curves and 24 ms for all eight; the Jacobian for par delta takes 12 ms and 77 ms (it uses finite differences). Redoing everything on every tick stays near 100 ms, and an analytic Jacobian should bring it to a few ms.
  • What is missing is not speed but how trades come in (alpha reads S# expression trees; qube holds an edited cashflow table) and the market's conventions (quote definitions, calendars, spot lag: alpha's bootstrap is a simplified reference).

1. How the Rates page computes today

  • Valuation is one call, IRatesPricingProvider.PriceBatchAsync (server/src/Qube.Samples.Rates/Pricing.cs). The provider in place is FakeRatesPricing (fake-rates/1, every figure simulated): a toy curve of pillar levels in percent, continuously compounded and linearly interpolated, and risk as a 1bp difference per pillar.
  • Input per line is the generated and edited cashflow table (each period's start, end, payment date, notional, rate and year fraction, plus notional exchanges), the direction, the leg to solve and the risk flag. Output is pv, parRate or fairSpread, and delta:{curve}:{tenor}.
  • Live keeps one calculation in flight with the newest market waiting; no Run per tick. A Price is one Run.
  • Rules: the Web server loads no calculation engine (CLAUDE.md, docs/08). For the Position Keeper (ADR-0019 §4) alpha runs as a separate process at a commit pinned in the flake, and an unreachable engine is refused, never replaced by a simulation. A missing value is never filled with a default.
  • Still open: each currency's conventions (C41: calendars, day counts, lags) and the list of risk factors (C38).

6. Proposed steps

  1. alpha: add the deterministic rates entry (TDD). Input: the cashflow table as JSON (legs, periods, exchanges, index, collateral) and quotes. Output: PV, par (or fair spread), zero delta, par delta. Same formulas as the flow table's Pv0, tested to agree with the same trade built from an expression tree. Make the Jacobian analytic. Whether the C++ version gets the same entry is decided later (C# alone is enough at first).
  2. alpha: the resident interface (takes a batch and answers; keeps curves by market snapshot id).
  3. qube: AlphaRatesPricing and starting the worker (commit pinned in the flake). Change the synthetic market from pillar levels to quotes (today's toy curve is not alpha's definition). Return risk as par delta under delta:{curve}:{tenor}.
  4. When conventions (C41) are settled, replace the quote definitions and calendars with the real ones.

Steps 1 and 3 in a first form (one JPY swap type, OIS and FLT-6M) look like a few days' work (an estimate). They touch no file the Position Keeper (PR #51) does, so both can go ahead side by side.

7. Decisions for the owner ("yes" accepts the recommendation)

  1. Connect by option A (persistent worker, alpha's C# version)?
  2. Send qube's cashflow table as it is, without building S# expression trees?
  3. Rates risk primarily as par delta to curve quotes, with zero delta returned for reference (an answer to C38's list of risk factors)?
  4. Until conventions are settled, use alpha's reference quote definitions labelled "unconfirmed"?
  5. Leave averaged RFR and in-arrears term rates out at first, refusing those lines with the reason?
