レーツ画面の時価・パーレート・リスクにalphaを使う

qubeのレーツ画面（金利スワップと通貨スワップの1行プライサー）で、alphaのカーブ構築とフロー表の評価を使えるかの調査と提案。2026-11-17。数値はすべて合成データ。English

答え: 使えます。ただし、今のalphaをそのまま繋ぐのではなく、alphaに「確定的な（モンテカルロを使わない）レーツの評価」の入口を1つ足し、qubeからは常駐する別プロセスのワーカーとして呼ぶ形を勧めます。

  • alphaの部品（カーブ構築、補間、フロー表の考え方、パーデルタのヤコビアン）で10年の円金利スワップを計算すると、PV、パーレート、ゼロデルタ（全節点）で1本12µsでした。勾配はバンプと小数2桁まで一致しました。
  • 重いのはカーブの側です。今のalphaの参照用ブートストラップは、円の2本で1.8ms、全8本で24ms、パーデルタ用のヤコビアンは円の2本で12ms、8本で77ms（差分で作っているため）。ティックごとに全部やり直しても100ms程度で、解析的なヤコビアンにすれば数msに下がる見込みです。
  • 足りないのは速さではなく、取引の受け取り方（今のalphaはS#の式木を読む。qubeは編集済みのキャッシュフロー表を持つ）と、市場の約束（クオートの定義、暦、スポットラグなど。alphaのブートストラップは簡略化した参照用）です。

1. qubeのレーツ画面は今どう計算しているか

  • 評価は IRatesPricingProvider.PriceBatchAsync（server/src/Qube.Samples.Rates/Pricing.cs）の1か所です。今入っているのは仮の FakeRatesPricing（fake-rates/1、結果はすべて simulated）。おもちゃのカーブ（節点の水準を％で持ち、連続複利で線形補間）で割り引き、リスクは節点ごとに1bp動かした差です。
  • 入力は、行ごとに生成と編集が済んだキャッシュフロー表（期ごとの開始日・終了日・支払日・元本・レート・年数、元本の交換）と方向、パーを解く脚、リスクの要否です。出力は pv、parRate か fairSpread、delta:{カーブ}:{年限}。
  • ライブでは、計算は同時に1つ、最新の市場が1つ待つだけ。ティックごとにRunは作りません。Priceは1回で1つのRunです。
  • 決まりごと: Webのサーバーは計算エンジンを読み込まない（CLAUDE.md、docs/08）。Position Keeper（ADR-0019 §4）では、alphaは別プロセスでflakeに固定したコミットを使い、届かなければ拒否してシミュレーションに切り替えない、と決めています。値が無いときに既定値で埋めることも禁止です。
  • まだ決まっていないこと: 通貨ごとの規約（C41、暦、日数計算、ラグ）と、リスクを出す要因の一覧（C38）。

3. 計測（スパイク）

alphaの Bootstrap.SolveAll、Bootstrap.Jacobians、Curves.Weights をそのまま呼び、スワップの評価と逆向きの勾配だけを小さなプログラムで書きました（alphaのフロー表は取引ごとに式木を要るため）。データはalphaの data/synthetic/small（評価日 2026-11-13、8本、各25節点）。Xeon 2.1GHz、.NET 10、Release、TieredPGO切り。

リスクの出し方: テープを使わず、逆向きの微分を手で書く

12µs の中のゼロデルタは、alphaのAADのテープ（Xva.Aad）を使っていません。スワップの時価は「各キャッシュフロー × 割引因子」の和で、割引因子とフォワードはカーブの節点の ln P の重み付きの和です。そこで、時価の式を後ろからたどり、各節点への感応度（∂PV/∂ln P）を足し込むコードを手で書いています（疎な勾配 SparseGrad）。

  • 原理はAADと同じ: 逆向き（随伴）に1回たどるだけで、全節点の感応度が出ます。違いは、計算の記録（テープ）を実行時に作らないことです。線形の商品では式の形が決まっているので、記録なしで済み、その分速くなります。
  • 確かめ方: 手で書いた微分は誤りが入りやすいので、ln P を ±1e−6 動かしたバンプと突き合わせるテストを置きます（alpha docs/spec/rates-pricer.md 第8節）。スパイクでは −122,395.63 円/bp で一致しました。
  • ゼロからパーへ: パーデルタは、ゼロデルタにクオートのヤコビアンの転置を掛けて出します（1カーブ約6µs、合わせて1行約18µs）。ヤコビアンは差分ではなく解析的に求める予定です（第4節）。
  • AADのテープが要る場面: スワップションのようにモンテカルロや非線形の評価が入る商品です。レーツ画面の範囲（線形の金利スワップと通貨スワップ）では使いません。

5. 繋ぎ方の案

案内容ライブの1ティック評価
A. 常駐ワーカーalphaのC#版に rates の入口を足し、1つのプロセスを常駐させる。qubeは IRatesPricingProvider の実装（AlphaRatesPricing）からローカルのHTTPか標準入出力でJSONを送る。カーブは市場のスナップショットごとに1回作ってワーカーに保持カーブ 2〜25ms＋ヤコビアン（今 12〜77ms、解析化で数ms）＋行あたり十数µs＋通信 1ms未満推奨
B. 呼ぶたびにexePosition Keeperと同じ。ファイルかJSONを渡して1回ずつ起動毎回 約300ms〜Priceには足りるが、ライブには遅い
C. qubeのWebに直接参照alphaのC#ライブラリをWebのプロセスに読み込む最速CLAUDE.mdとADR-0019 §4に反する（libmのP/Invoke、TieredPGOの設定、エンジンの更新がWebの再起動に縛られる）
D. WASMでブラウザブラウザで計算速いRunやPriceの記録、プロバイダの同一性が崩れる。勧めない
E. qubeに小さい評価を移植スワップの式だけqubeに書く速いXVA側のカーブと割引がずれる。エンジンが2つになる

Aでも、ワーカーに届かないときは行を「計算できない」として示し、仮のプロバイダには切り替えません（CLAUDE.mdの決まり）。結果の札は「real engine / synthetic market」になります。

6. 進め方の提案

  1. alpha: 確定的なレーツ評価の入口を足す（TDD）。入力はキャッシュフロー表のJSON（脚、期、元本の交換、指標、担保）とクオート、出力はPV、パー（またはフェアスプレッド）、ゼロデルタ、パーデルタ。フロー表の Pv0 と同じ式で、式木から作った同じ取引と値が一致することをテストする。ヤコビアンを解析的にする。C++版にも同じものを入れるかは後で決める（最初はC#版だけで足りる）。
  2. alpha: 常駐の口（バッチを受けて返す。市場のスナップショットのIDでカーブを保持）。
  3. qube: AlphaRatesPricing とワーカーの起動（flakeで固定したコミット）。合成市場を「節点の水準」から「クオート」に変える（今のおもちゃのカーブはalphaの定義とは別物のため）。リスクの列を delta:{カーブ}:{年限} のパーデルタで返す。
  4. 規約（C41）が決まったら、クオートの定義と暦を本当のものに替える。

1と3の最初の形（円のスワップ1種類、OISとFLT-6M）までなら、数日の規模と見ています（見込み）。Position Keeper（PR #51）とは触るファイルが重ならないので、並べて進められます。

7. 決まったこと（Akira、2026-11-17）

  1. 繋ぎ方: サーバー側は常駐ワーカー（案A、alphaのC#版）。
  2. 取引: qubeのキャッシュフロー表をそのまま渡す。S#の式木は作らない。
  3. リスクの表示: パーデルタとゼロデルタをスイッチで切り替える。既定はパー。ワーカーは両方を返す（ゼロからパーへの変換はJᵀを掛けるだけで、1本数µs）ので、切り替えで計算し直さない。
  4. 平均型RFRと後決めのターム物: 最初から入れる。
  5. 市場の更新: 本番では作り終えたカーブとヤコビアンが1秒に1回届く（クオートではない。16:40 に訂正）。下の第8節の時間の割り振りはこれに合わせる。
  6. クオートの定義は、まだ返事が無いので、規約（C41）が決まるまでalphaの参照用の定義を「未確認」の札付きで使う（推奨どおり。変えるなら言ってください）。

8. 1秒ごとの更新に収まるか

前提の訂正（Akira、2026-11-17 16:40）: 本番で1秒ごとに届くのはクオートではなく、作り終えたカーブ（割引因子の節点）と、パーデルタ用のヤコビアン J = dz/dqです。ワーカーはカーブもヤコビアンも作らず、読むだけです。XVA の入力（割引因子とヤコビアン）と同じ形です。

  • ゼロデルタ: 届いたカーブの ln P の節点への勾配。
  • パーデルタ: ゼロデルタに届いた Jᵀ を掛けるだけ（1カーブ約6µs）。
  • カーブとヤコビアンは、スナップショットごとにワーカーで1回だけ受け取って保持し、すべての利用者とワークスペースで共有する。読み込みは数ms の見込み（未計測）。
  • 時間の見込み: 30人×50行で約30ms、90人で約80ms（1行約18µs）。1秒の更新に十分収まる。先に詰まるのは計算より、結果の JSON の量（30人の解説書）。
  • 計算が1秒を超えたときは、今のライブの決まりどおり、計算中の1つの後ろには最新の市場だけを待たせ、古い市場は飛ばす（ティックを積み上げない）。
  • クオートからカーブとヤコビアンを作る部品は作らない（CurveSet.Build は取りやめ）。合成データで画面を動かすときは、alpha の合成の市場データ（割引因子とヤコビアン、XVA の入力と同じもの）をそのまま渡す。

9. まだ決めること

  1. 後決めのターム物の凸性の調整（決定、Akira、2026-11-17: alphaのハル・ホワイト）: 期間の終わりに決まる金利を同じ日に払うので、時価に凸性が効く。ボラティリティが要る。推奨は、alphaのハル・ホワイト（平均回帰と、スワップションのATMボラティリティから求めたσ）で調整すること。XVA側と同じモデルで、alphaにはキャリブレーションがある。このためqubeの合成市場にスワップションのATMボラティリティの面を足す。
  2. 平均型RFR: 日次のフォワードの単純平均で評価し、凸性（とても小さい）は入れない。仕様に書いて札を付ける。
  3. 実装の境界（TDDの前に合意する）:
    • alpha: Xva.Rates（純粋な関数）。CurveSet.Build(クオート, 定義, 評価日) がカーブとヤコビアンを返し、RatesPricer.Price(CurveSet, 行の並び) が行ごとにPV、パー（またはフェアスプレッド）、ゼロデルタ、パーデルタを返す。行はキャッシュフロー表（脚、期、元本の交換、指標と後決めの種類、担保）。
    • alpha: xva-rates-worker（常駐。1行1つのJSONを標準入出力で受けて返す。スナップショットのIDでカーブを保持）。
    • qube: AlphaRatesPricing : IRatesPricingProvider がワーカーを起動して呼ぶ。合成市場はクオートを出す形に変える。リスクの列の切り替えはクライアントの表示だけ。

計測に使ったプログラム: プロジェクトファイルの rates/alpha-rates-spike/Program.cs（alphaの main 0558823 に対してビルド）。
