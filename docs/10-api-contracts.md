# API and contract starter

All routes and type names here are proposed. Adapt them to an existing host without changing the domain invariants. `contracts/*.schema.json` describes a bounded starter vocabulary; it is not the company analytics wire protocol.

## Endpoint responsibilities

| Endpoint proposal | Purpose and invariants |
|---|---|
| `GET /api/quant/counterparties?query=...` | Fuzzy authorized search; return registration ID plus CP code, legal entity, name and special flag. |
| `POST /api/quant/workspaces` | Create an editable workspace, not a pricing run. |
| `POST /api/quant/workspaces/{id}/prepare` | Resolve a context change; return immutable source snapshot IDs and dependent data; echo preparation generation/context. |
| `POST /api/quant/trade-inputs/import` | Resolve draft booking IDs to immutable TradeInput versions before a Run exists. |
| `PUT /api/quant/workspaces/{id}/draft` | Optional draft persistence with expected server version; no implicit execution. |
| `POST /api/quant/analysis-runs` | Validate/freeze effective input or a fully bound workflow, persist a Run and enqueue required work. Idempotent. |

| `POST /api/quant/analysis-runs/{runId}/cancellation` | Record cancellation requested; does not imply provider cancellation succeeded. |
| `GET /api/quant/analysis-runs/{runId}/diagnostics` | Authorized manifest and diagnostic bundle, including legacy locations through the same abstraction. |
| `GET /api/quant/data/{id}/rows` | Authorized projection/filter/sort over a fixed dataset revision. |
| `POST /api/quant/rates/subscriptions` | Open/update a live workload; streaming transport separately bound to subscription ID. |
| `POST /api/quant/rates/subscriptions/{id}/capture` | Persist the exact selected complete frame and its input/market refs. |
| `POST /api/quant/definitions` | Save a validated workflow/view version; execution is separate. |
| `POST /api/quant/agent/...` | Adapter-owned AG-UI endpoint using a pinned verified protocol implementation. |
| `POST /api/agent/commands/{capability}/{version}` | A command capability (ADR-0005) as the agent's tool call reaches it: inputs checked against its contracts, an idempotency key, the caller set by the server with origin `ai`; no Run. Since step 4a (ADR-0016 §7, note 38) three of them read a workspace and are typed on no line (effect `readWorkspace`, no `command` in the catalog; refused as a workflow step). Each takes port `request` and answers port `answer`, for the caller's own workspace at the `revision` given or the one it holds. `tables.describe` (`{ workspaceId, revision?, table? }`) answers `{ workspaceId, revision, app, tables, fields }`: `tables` `[{ table, version, title, words, key, rows, subsets, singleRow, main }]` and `fields` `[{ table, name, title, words, form, written, editable, optional, choices?, moreChoices?, unitField?, pointsTo?, group? }]`, where `written` says how a value is typed and `choices` holds at most 50 with the rest counted in `moreChoices`. Since step 5a (notes 46 and 47) a table under another's rows says it (`under`, the table above), and a field that is a figure of the rows under its row says the table it is a figure of (`figureOf`) and what its number is in (`unit`); its `written` is how the figure is written, which may be a number with a unit where it reads as a number. `tables.read` (`{ workspaceId, revision?, table?, rows?, fields?, start?, limit? }`, `rows` as `entity.set` takes them and left out only for a table of one row, `limit` 1 to 200 and 50 where left out) answers `{ workspaceId, revision, table, count, start, fields, rows, more }`: `rows` `[{ key, subset?, cells }]`, each cell the text `set` reads back, in the order of `fields`; a page holds at most 2,000 cells, `count` is every row the selector matched and `more` how many follow the page. With no field the rows are their keys. `commands.preview` (`{ workspaceId, revision?, line }`) answers `{ workspaceId, revision, line, command, version, inputs, arguments, would, table?, rows?, count?, first?, expands?, at? }`: `inputs` is JSON text to hand to the command's own tool, `arguments` `[{ name, text }]`, and nothing is run. Each is refused as a line is (422 with the code, the sentence, the `word` at fault and `candidates`): an unknown table, field, subset or row, `FieldTwice`, `NoRows`, and `NoView` for `selected`, `shown` and a verb of the screen, which a caller with no screen has not; 403 `NotOwner`, 404 `UnknownWorkspace`, 409 `RevisionMoved`, and `ValidationFailed` for a `limit` over 200 or a `start` no position holds. |
| `POST /api/commands/{capability}/{version}` | The same command as the page reaches it (ADR-0016 §5): the same checks and the same answers (404, 403, 409, else 422), the caller set by the server with origin `pricer`. `entity.set`, `entity.reset`, `entity.remove`, `workspace.undo` and `workspace.redo` (ADR-0016 §3, §11) are what the pricer's page runs through it, with the pricer's own verbs that edit (note 28): `xva.vary`, `xva.trades.add` (`add each`), `xva.cds`, `xva.measures`, `xva.case.remove` and `xva.cases.clear`. The page's endpoints that wrote for those are gone: `/vary`, `/cds` (the write), `/add-trades`, `/cases/remove`, `/cases/clear` and `/measures` under `/api/xva/workspaces/{id}`. Since step 3b (notes 32 and 33) the ten scenario commands (`xva.scenario`, `xva.scenario.include`, `.exclude`, `.remove`, `.duplicate`, `.ladder`, `.cross`, `.load`, `.save` and `xva.scenarios.clear`), `xva.workspace.price`, `xva.refresh` and `xva.pv01.retry` go the same way, and `/scenarios` with everything under it, `/price`, `/refresh` and `/retry` are gone with `GET /api/xva/scenario-sets`; the Scenarios grid's own edits stay `/shifts`. `xva.workspace.price` answers `{ workspaceId, revision, said, runId }` and submits its Run under the request's `idempotencyKey`, which the gateway hands to the handler: the same invocation sent twice is one Run. Its effect, and `xva.pv01.retry`'s, is `execute` (it starts something `undo` does not take back). `xva.refresh` answers `{ workspaceId, revision, said, carried, conflicted, lost, stays }`. Since step 3c (notes 34 to 36) a Rates workspace is reached the same way: the kernel's verbs over `rates.lines` and `rates.workspace` (its defaults), `entity.create` (`new <product> <terms>`; request `{ workspaceId, revision?, product, terms }`, answer `entity`: `{ workspaceId, entity, revision, product, said, defaulted }`), `rates.line.add` (`{ product }`; answers `{ workspaceId, revision, said, line }`), `rates.workspace.price` (`{ marketSnapshotId? }`, the latest where it is left out; answers `{ workspaceId, revision, said, runId, marketSnapshotId }`, one Run under the request's `idempotencyKey`), `rates.frame.capture` (`{ subscriptionId, subscriptionRevision, inputRevision, marketSnapshotId }`, all four or none, none meaning the frame shown as it runs; answers `{ workspaceId, revision, said, runId, marketSnapshotId }`) and `rates.live.start` and `rates.live.stop` (port `workspace`: `{ workspaceId }`; answer `subscription`: `{ workspaceId, subscriptionId, revision, said }`). The page reads a command's output named `answer`, or its one output. Gone with them: `POST /api/rates/workspaces/{id}/lines`, `/lines/new`, `/lines/{line}/remove`, `/defaults`, `/price` and `/live`, `POST /api/rates/live/{id}/capture`, `DELETE /api/rates/live/{id}`, `GET /api/products` and `POST /api/products/{id}/preview`. What stays under `/api/rates`: the market, a workspace's list, creation, view and deletion, a typed cell's edit (`/lines/{line}/edits`), the cashflows and their edits, resolutions, the valuation date, and a subscription's frames (`/live/{id}/frames`). Since step 3d (note 37) `xva.trades.add`'s request may hold `iterations`, a list of `{ add: [ids], without?: [ids] }`: the new trades a case adds together and the existing trades it takes out of After. It is the whole set: the cases of `add each` made before are replaced, and a New row with A ticked that none names is one more case alone. With `keep: true` (note 37, corrected in review) the cases made before stay as they are and the iterations given are made beside them: one made already is refused (`AlreadyMade`), and `keep` with no iteration is refused (`NothingGiven`). Left out, the command is `add each` as typed. A case of kind `add` names its `iteration` (`{ add, without }`) in the workspace's view and in the input Price freezes, where it named one `trade`. A contract's field may be a list (`type: array` with `items`, of values or of records whose fields are values or lists of values); a list's problem is said at its path (`/inputs/request/iterations/0/add`). |
| `GET /api/catalog` | What the server declares, read once by the client: the capabilities, each command with how it is typed (`command`: its words and arguments, ADR-0016 §4), and apart from them the verbs of the screen the server reads (`viewVerbs`: `verbId`, `title`, `command`; ADR-0016 notes 21 and 39): `find`, since step 4b `sort` and `filter`, and since step 4c `select`, `copy` and `export`. A view verb is no capability: nothing invokes it, and the agent's tools hold none. A command's `command` may name the application of the workspaces it acts on (`app`, note 27): the line lists it on that application's pages alone. `shortForms` (`formId`, `title`, `command`; note 29) lists the words that stand for a line of another command; like a view verb, a short form is no capability and no tool of the agent's. `draftCommands` (ADR-0016 note 55, since step 5c) lists the ids of what is read while a row's draft is open (`entity.set`, `entity.reset`, `entity.create`, `entity.remove`, `draft.apply` and the verb `cancel`): a line lists every other served command as unavailable while a dialog is open. |
| `POST /api/commands/preview` | Reads a line as typed for a workspace and executes nothing (ADR-0016 §5, note 15). Request: `{ line, workspaceId, revision?, view? }`, where `view` is what the user was looking at when the line opened (notes 16 to 19): `{ table, subset?, sorts?, order?, keys?, ranges?, focus?, shown?, where? }`, its selection by row keys or by ranges of positions in the order `order` names, `focus` a cell (`{ field, key? }` or `{ field, position? }`), `shown` the keys of the rows a page that holds every row shows where its grid filters them by its own columns, and `where` the conditions the grid holds from `filter` (note 41), as typed, for which a view names no row: the server reads which rows they leave. Under `where` the word `shown` is the rows the conditions leave, of the rows `shown` names where both are given, and a position is one among those rows; conditions that can no longer be read (a field gone) leave the view's sentence saying so with `viewMoved` true, and refuse `shown`, `find` and positions (`FilterUnread`). Answer (200): the revision read, the command (`id`, `version`), its `inputs` ready to post to the gateway (rows of a screen resolved to their keys, and the table named where the screen gave one the line left out: note 23), each argument as read with where it came `from` (`typed` or `context`), the view in one sentence (`view`, with `viewMoved` true where its positions are of an order that has moved since), the rows (`table`, `title`, `count`, `first`), what would change in one sentence (`would`, and `at` where it speaks of a moment), the line a short form stands for (`expands`, note 29: the command, inputs, rows and `would` are then that line's), `asks` and no command where the line is a view verb's (note 42, since step 4c; before it the members `place`, `sort` and `filter`): the one thing asked of the page, said by its `kind`, each with `said`, the sentence once it is done. `place` (note 21) is `{ kind, table, subset?, key, position?, column?, said }`, the position in the order the view names with `order` and left out where it names none. `sort` and `filter` (notes 39 to 41) are `{ kind, table, subset?, sorts: [{ column, descending }], said }`, the grid's columns with the major key first and none for `sort off`, and `{ kind, table, subset?, where?, said }`, the conditions as typed for the grid's view to carry and none for `filter off`, with `rows` the rows they leave. `select` (note 43) is `{ kind, table, subset?, position?, keys?, count, column?, said }`: one run of rows, by its first position in the view's order where the server pages the grid, and by the rows' keys where the page holds every row and says itself whether its grid shows them next to one another. The page gives each of these four to the grid the view was read of. `copy` is `{ kind, said }` and `export` `{ kind, fileName, said }` (note 44): the page's door asks `POST /api/commands/content` for the cells and puts them on the clipboard or saves the file. Or `refused` (`code`, `sentence`, the `word` at fault with its `start` and `end` in the line, `candidates`; since step 4d a domain verb's refusal names its word and candidates too, note 45); and what could follow the last word (`complete`: `value`, `start`, `detail`; `more`). A line that cannot be read is an answer, not an error. 400 `InvalidView` for a view that names what the workspace has not or is no view (a range of no row, a selection said two ways), 404 for an unknown workspace, 403 for another user's, 409 where a revision is given and the workspace has moved. Since step 5c (ADR-0016 notes 54 to 56) `view` may carry `draft`, a row's draft as its page holds it: `{ table, key, revision, lines }`, the lines whole lines of the workbench that name the row. With one the server reads the line for the draft's row on the state its lines leave, at the draft's revision, whatever else the view says. `set`, `reset`, `new` and `remove` then answer no command but the ask `draft` (`{ kind, line, said }`): the whole line the draft gains, for the page to add; `apply` answers the command `draft.apply` with the draft as its inputs; `cancel` answers the ask `cancel` (`{ kind, said }`), and is read though the workspace has left the draft; every other command and verb is refused (`DraftOpen`), a line of another row is `NotTheDraftsRow`, one that changes nothing `NothingToAdd`, and one that removes the draft's own row `RemovesTheDraftsRow`. With no draft, `open <row>` answers the ask `open` (`{ kind, table, key, said }`): the one row whose dialog the page opens, at the revision read; `apply` and `cancel` are then `NoDraft`. |
| `POST /api/commands/content` | The cells `copy` or `export` takes out of a workspace (ADR-0016 note 44), asked for at Enter by the page's door; nothing is executed, written or logged. Request: `{ line, workspaceId, revision?, view? }`, as the preview's: the server reads the same line again at `revision`. Answer (200): `{ revision, text }`, or `{ revision, refused }` with the refusal a preview of the line would give (`code`, `sentence`, `word?`, `candidates`), and `NoContent` for a line that is neither verb's; a short form is followed to the line it stands for. For `copy` the text is the rows as lines of cells apart by tabs, CRLF between lines and none after the last, with no header line unless the line ends `with headers`. For `export` it is comma-separated values (RFC 4180) that begin with a byte order mark, a header line of the words that name the fields, and CRLF after every line. A cell is written for a spreadsheet to read as the value held: an amount, a number and a count of days in full with no grouping, a rate and a spread with the percent sign, a flag `true` or `false`, a date `yyyy-mm-dd`, no value empty; a text is written as it is. A line of one empty cell is written as a quoted empty cell (`""`), never a blank line. More than 1,000,000 cells are refused (`TooManyCells`). 400 `InvalidView`, 404, 403 and 409 as the preview. |
| `GET /api/workspaces/{id}/tables` | The tables of a workspace with the actions worth an item of a grid's Context Menu (ADR-0016 §4, note 25). Answer (200): `[{ tableId, title, actions: [{ title, line }] }]`, the kernel's `Reset this cell` (`reset`) first on every table that takes it, then the table's own (`Take out of After`, `set selected after off`). A page runs an action's `line` as a line typed, through `POST /api/commands/preview` with the menu's view, and the command it reads. 404 for an unknown workspace, 403 for one that is not the caller's. An action whose line begins with no command's words is the registration's defect and fails the read. |
| `POST /api/workspaces/{id}/shown` | The rows a view's grid shows under the conditions it holds (ADR-0016 note 41), for a page that holds every row of its grid: it asks at each revision it shows, and shows the rows named. Request: `{ view }`, the view as the preview takes it. Answer (200): `{ table, revision, keys, of }`, `keys` read as the preview reads `shown` and `of` how many rows the grid has with no conditions. It writes nothing. 422 `FilterUnread` where the conditions cannot be read (the page then shows no row and says why), 400 `InvalidView`, 404 for an unknown workspace, 403 for one that is not the caller's. |
| `POST /api/workspaces/{id}/draft` | The form of a row's draft (ADR-0016 notes 54 and 57, since step 5c), which a page draws the row's dialog from; it writes and stores nothing. Request: the draft, `{ table, key, revision, lines }`. Answer (200): `{ table, word, key, revision, fields, under, templates, lines, original? }`. `fields` are the row's fields in the table's order, each `{ field, written, changed }`: `field` says how it is typed (`name`, `title`, `word` a line says it by, `group?`, `editable`, `optional`, `form`, `takes` in words, `choices?`, `unit?`, `figureOf?`, and `number`, whether it holds a number), `written` is its value as a line writes it (`empty` for none) on the state the draft's lines leave, and `changed` whether the draft changed it. `under` is each table under the row, `{ table, title, word, fields, rows, makes }`: its fields without the one that names the row above (all kept where several point into the table above), its rows as the draft leaves them (`{ key, written, mark? }`, `written` in the fields' order and `mark` one of `made`, `changed`, `removed`), and `makes` the products that make a row there (`{ word, title, takes }`, the row above left out of `takes`). `templates` are the table's, `{ word, title, takes }`, each term `{ name, title, required, form, takes, choices? }`. `lines` are the draft's lines as read in order, each `{ line, said }` or `{ line, refused: { code, sentence } }`; the reading ends at a line that no longer reads, and the form is that of the lines before it. `original` is the row as the source alone gives it (`{ written, under }`), left out for a row the workspace made. 409 `RevisionMoved` for a draft the workspace has left, saying the revision it is at and the commands that moved it; 404 `UnknownTable` or `UnknownRow`, and for an unknown workspace; 403 for one that is not the caller's. The draft is written by the command `draft.apply` (`{ table, key, revision, lines }` as its request), one batch that one `undo` takes back: refused `RevisionMoved` where the workspace moved, `DraftUnread` where a line no longer reads (one that changes nothing by then among them), saying the line's number and its refusal, and `NothingToApply` for a draft of no line. It is a command as any other, so the AI's tools hold it (note 55). |
| `POST /api/xva/workspaces/{id}/rows` | A page of one of the pricer's trade grids, which the server pages (ADR-0010 §6). Request: `{ start, count, sorts, grid, where? }`, `grid` `new` or `existing`, and since step 4b `where`, the conditions the grid holds from `filter` (note 41). Answer: `{ rows, start, totalCount, orderToken, revision, pvCurrency, of? }`; `pvCurrency` is the currency every row's `pv` is in, the display currency as the page was read, which the grid's PV header names (ADR-0016 note 49). Under `where` the rows are those the conditions leave, in the reader's order, read by the kernel as a line's reading of `shown` reads them: `totalCount` counts them, `of` is the count with no conditions, and `orderToken` is of them alone, so it moves when a row enters, leaves or moves among them and only then. Conditions that cannot be read are refused (422 `FilterUnread`), never ignored; a column the reader does not sort by is refused as before. Since step 5a (ADR-0016 note 49) a row carries `pv`, the trade's PV legs added up in the display currency, absent where the trade has no leg; `original.pv` is what the source's legs give where the workspace's differ; and `pv` is a column the reader sorts by. The legs themselves are rows of the table `xva.legs`, read and written by the table capabilities, and are not in this answer. |
| `POST /api/workspaces/{id}/selection` | The keys a view's selection names (ADR-0016 note 37), for a page that makes a typed value from a grid the server pages. Request: `{ view }`, the view as the preview takes it. Answer (200): `{ table, keys }`, read as the preview reads `selected` (note 17), and no key where nothing is selected. It writes nothing and runs nothing. The view is checked whole before anything is read, whether or not it selects a row: 400 for a view that cannot be read (`InvalidView`: a table, a subset or a column the workspace has not, positions on a table with no order), 409 where the order the selection was written in has moved (`ViewMoved`, to be read again), 404 for an unknown workspace, 403 for one that is not the caller's. |

Endpoints map transport inputs to application services. Tests call those services and pure domain functions without starting Blazor or MQ. Read-only capability discovery may be tailored to the caller's permissions.

## Saved sequences of edits (ADR-0016 §8, notes 60 to 64, step 6)

Two command capabilities of the kernel, of every application, reached through the two command endpoints above as any command is. A sequence is a saved item (C32): kept under `sequence:<app>`, its owner's alone unless shared, named `<name>` or `<name>@<owner>`.

- **`sequence.save`** (`sequence save <name> [desk|all] <line> then <line> …`). Request `{ workspaceId, name, share?, lines }`: `workspaceId` a workspace of the caller's, which says the application and is what the lines are checked on; `share` is `desk` or `all`, and left out the sequence is the caller's alone; `lines` the lines in order, one to fifty, each a command as a person types it. Answer `{ workspaceId, revision, said, name, owner, share, desk?, lines, replaced }`: `revision` is the one the workspace stands at, since a save moves none and is in no log; `share` is `private`, `desk` or `all`; `lines` is how many were kept. Refused (422), with nothing kept: `ValidationFailed` (no line, or a share other than `desk` and `all`: the request's contract), `InvalidName`, `NoDesk`, `TooManyLines`, `EmptyLine`, `NotACommand` (a line that begins with no command's words), `NotInASequence` (a verb of a page, `undo`, `redo`, `apply`, a `sequence` verb, a command that neither edits the workspace nor starts work on it), `NoView` (`selected` or `shown`), `ExecutesBeforeTheEnd` (a command that starts work, such as `price`, before the last line). Each of the last five names the line by its number. A line that names a command and is refused only as the workspace stands is kept, and `said` names each such line and why. The line as it is typed with no line yet reads `NoLines`.
- **`sequence.run`** (`sequence run <name>`). Request `{ workspaceId, revision?, sequence, saved? }`: `sequence` is `<name>` or `<name>@<owner>`; `saved` is the moment the sequence was saved as a reading of the line said it, and a sequence saved again since is refused. Answer `{ workspaceId, revision, began, said, sequence, owner, lines, ran, steps, stopped?, stoppedCode?, stoppedWhy?, stays? }`: `began` and `revision` are the revisions the run began at and left the workspace at; `steps` holds each line that ran, in order, as `{ number, line, command, said, revision, answer }`, where `command` is the capability id the line named and `answer` is that command's own answer, whole, as JSON text (the id `undo` names, a Run a `price` started). Each line is its own command in the workspace's log, with origin `workflow`, or `ai` where the agent's endpoint ran the sequence.
- **A run that stops.** A first line that is refused refuses the command with that line's code and nothing run. A later one ends the run and the command is done: `stopped` is the line's number, `stoppedCode` and `stoppedWhy` its refusal, `ran` and `steps` the lines before it, which stay written, and `stays` is true. `said` then says what `undo` reaches of them: a line whose command no undo takes back (one that took another source version, for one) keeps `undo` from itself and from the lines before it. `stays` is also true where a line's own answer said `stays`, and `said` then holds that line's sentence with its number. Refused before any line: `UnknownSaved`, `AmbiguousSaved`, `SequenceMoved`, `RevisionMoved` (409), and from the line `SequenceNotNamed` and `UnreadWords`. A line whose first words name another command than when it was saved stops the run as `LineMoved`.
- **Asked again with the same idempotency key**, a run answers what it answered; each line is invoked with the key and its number.

## XVA accepted input

`examples/xva-final-input.json` shows a submitted full effective input subset:

- Context and pinned baseline/market versions.
- Effective CDS/proxy and separate recovery settings.
- NS legality, CSA definitions/selection and scenario definitions.
- Every relevant trade row with immutable TradeInput reference, B/A membership and explicit assignments.
- Calculation options and separately stored user/automatic provenance.

`examples/xva-uncollateralized-input.json` covers the optional-CSA case. An explicit `uncollateralized` selection uses the reserved CSA value `nocsa_{ma id}` (for example `nocsa_MA-001`), with no real collateral agreement required. The initial UI's corresponding main selection uses the same marker; its real CSA collection may be empty. Validate the marker against the trade's effective MA; it is not an unresolved choice or a real CSA master record. The default uncollateralized discount curve is configurable, for example `jpy_ois`, and is resolved into the visible typed row during preparation. Price preserves the final row curve, including any later manual override. A source/config version can be recorded through `defaultsProfileRef`.

When `cvaRecoveryOverride` is null/empty, preserve it as null/empty in the company engine request: analytics automatically uses the applicable CDS recovery already supplied in the fixed credit data. No additional `effectiveCvaRecovery` field is required and no explicit override is synthesized. An explicit numeric zero remains zero. Mapping empty wire representation and selecting the applicable CDS record follow the real analytics contract. This documented fallback is part of the accepted semantics, not an excuse to refetch credit data or change user settings.

In iterative mode, `candidateTradeInstanceIds` is a derived consistency projection of all eligible New rows checked for After, unique and nonempty; it cannot independently omit a checked row. The server verifies this equality before case expansion.

### What the sample pricer's accepted input carries (ADR-0016 note 53, step 5b)

The sample's accepted input holds a list of `cases`, the Base first. Since step 5b each case carries what a user can set, as set, whether or not a simulated measure reads it:

- Each trade of `trades` carries `legs` (`legId`, `currency`, `pv`, `notional`, the notional `null` where the leg holds none), `independentAmounts` (`amountId`, `currency`, `start`, `end`, `value`) and `details`, the trade's fields beyond the grids by name (identity, agreement, break and model). A trade with no leg or no independent amount carries an empty list, and an empty field of `details` is `null`: neither is left out. The PV the legs add up to is not carried; it is a figure of the legs in the display currency, which the input names.
- `csas` holds every CSA a trade of the case uses, in the CSA table's order: the terms the page shows, and under `details` its general terms and what each side posts. A trade under no CSA carries the agreement's `nocsa_{ma id}` as its `csa`; that names no CSA and has no entry in `csas`, so an uncollateralised counterparty's `csas` is empty.
- A trade's PV is not carried: it is a figure of its `legs` in the display currency the input names.
- A case made by `vary` or `add each` carries its own values in the same places.
- Since step 5d (ADR-0016 note 59) the input names the booked trades the workspace loaded and the store has on the value date, in the order they were loaded (`loadedTrades`, a list of ids beside `nettingSet`, empty where none was loaded), and the version of the store their terms were read from (`loadedTradesVersion`, `booked@<value date>#<trades it has then>`; null where none was loaded). Each is in `trades` as any new trade is, with its terms, legs, independent amounts and `details`, unless the case leaves it out of After. `sourceVersion` stays the counterparty's source's: a load does not change it.

What the simulated measures read is unchanged: an existing trade's `officialPv`, and for SA-CCR the CSA terms under `modules.ccr`. The input so holds both an official PV and the legs, and which of them the real analytics request reads is decided when it is connected.

### What step 5d adds to the sample pricer (ADR-0016 notes 58 and 59)

- **`xva.trades.load`** (`load trades <ids>`), a command capability as the others are: request `{ workspaceId, revision?, trades }`, `trades` the ids of booked trades separated by commas or spaces, whatever their case; answer as every edit of the pricer answers (`Edited`). It reads a synthetic store of forty booked trades, `B00001` to `B00040`, of no counterparty, as of the workspace's value date. Refused (422), with nothing loaded: `NothingToLoad`, `GivenTwice`, `UnknownTrade` (an id the store has not, or a trade past its maturity on the value date) and `TradeHeld` (loaded already). A value written on a trade of the store the workspace has not loaded, or on its leg or independent amount, is refused `UnknownTarget` whichever endpoint it came through.
- **`remove trades <id>`** (`entity.remove`) removes a loaded trade with its edits and the legs made under it, as one command. Refused: `TradeInCase` while a case holds a change of the trade, and `ConflictUnresolved` while an edit of it waits as a conflict. A trade the source gave is refused as before.
- **A trade grid's `orderToken`** moves when a booked trade is loaded or removed, as it moves with a new source version: rows chosen before are refused `ViewMoved` after. The Existing grid's does not: it holds no loaded trade.
- **Two tables**, read and written through the kernel's verbs as any table: `xva.scenarios` (`scenarios`; fields `scenarioId`, `name`, `count`, `included`, `issue`; `included` is the one a command sets) and under it `xva.shifts` (`shifts`; fields `shiftId`, `scenario`, `category`, `index`, `factor`, `type`, `size`, `description`, `issue`; `index`, `factor`, `size` and `description` are set). A scenario's key is its name with every run of characters other than letters, digits and `_ + - % .` written as `_`; a key that is a word that says rows (`all`, `selected`, `shown`, `where`, `as`) gains a `_`, and of two names that give one key the later in the scenarios' order gains `_2`, the next `_3`. A shift's key is `<scenario key>/<number>`. An id that is a scenario's whole key names its shifts (`shifts up`), read before the end of a shift's key. An FX shift's `factor` is `spot`, and `all` is refused for it. A shift's `size` is `{ amount, unit }` with `unit` `bp` or `%`, written `+10bp` or `-5%`; a size with no unit is refused `InvalidShift`. `reset` of a scenario is refused `NotResettable`.
- **`tables.describe`** lists, for a field that holds a number with what it is in, the units it may be in (`units`). A condition on such a field says its unit (`where size > 5bp`); a number alone is refused `InvalidValue`. Equal is the same number in the same unit, so `!=` holds of a value in another unit; an order (`<`, `>`) is among the values in the unit asked.

The `synthetic` field in these fixtures is an advisory source-data marker only. Real/mock execution provenance and source origin are determined by the server from actual source/provider records, not trusted from client input. A real engine using synthetic markets is still actual computation on synthetic data.

The example uses explicit rows for clarity. A very large portfolio may instead reference an immutable complete dataset revision plus a fixed resolved selection set. This must be logically equivalent and cannot mean only the viewport or a filter evaluated later against mutable data.

`workspaceRevision` identifies the locally visible accepted edit revision. If draft persistence is enabled, use a separate server ETag/expected-version check; do not assume a client counter alone prevents concurrent writes. Price may atomically persist the submitted complete draft and its Run. A conflict returns a structured error; it does not merge economic fields silently.

`schemaVersion` is the contract version, not an engine version. The server computes the authoritative accepted-input digest using a documented canonical encoding. A raw file SHA-256 is a separate byte-integrity digest. Client digests are consistency hints, not trusted proof. Preserve semantically significant ordering and units.

## Typed reference

Use a data ID, immutable revision and explicit contract identifier/version. Resolve contents through authorized services. `dataId` is not a file path, and knowledge of it grants no access. For artifacts, preserve actual media type, schema/format version, byte digest and producing invocation. Small typed values may be embedded instead of stored separately.

## Workflow starter vocabulary

`examples/simm-comparison.input.json` supplies the resolved case/MA/CSA/curve and fixed source bindings used by the Workflow. Its domain-specific schema is separate from the generic composition schema. A real source adapter resolves these example references; this bundle contains no company snapshots.

The example workflow uses `input`, `context`, `constant`, `output` and `item` bindings. `forEach` maps a step over a typed collection with bounded concurrency. Every mapped output is lifted to `Outcome<T>[]`: each envelope contains a stable `itemKey`, status, domain identity metadata, and either a value or an error. Consumers cannot infer identity from completion order.

With `itemMode: value`, the source is a plain input collection and `itemKeyPath` supplies its unique stable expansion key. The CRIF step uses this mode. With `itemMode: outcomeValue`, the source is a prior mapped output; the runtime binds `item` to the successful envelope's `value`. Failed/blocked upstream envelopes do not invoke the downstream capability; they produce a blocked outcome with the same item identity. The SIMM step uses this mode. The comparison step consumes the complete `qube.simm-side-outcome` collection plus the original planned comparison, so cases with both sides failed remain present with unavailable values. `collect` does not mean errors disappear.

The runtime records expanded invocation keys such as `crif/case-A/before` and `simm/case-A/before`, distinct from the definition's `stepId`. Their construction is stable across retries. In the SQL sketch, `step_key` stores this expanded key, so map iterations do not collide under the per-Run uniqueness constraint.

`dependsOn` is explicit and must agree with output bindings. `outputs` names stable workflow output ports. Bindings use JSON Pointer paths within declared contracts; no executable expressions are permitted.

Generic dataset schemas contain column/row structure and generic execution/data-origin provenance. Domain basis metadata is a versioned extension; the SIMM fixture's value date, market, methodology and currency live there. The generic kernel does not interpret those financial fields.

The sample CRIF generation occurs per prepared portfolio side. A real domain adapter may compute deltas or reuse common sensitivities if mathematically valid and represented by compatible lineage; this optimization is not assumed by the sample.

## Numerical result semantics

Return values together with currency/unit, measure definition, status, provider ID/version, engine/model/config version, value date, data versions and input/result references. A numeric null with failure/unavailable status is not zero. Compare results only when their bases are compatible.

The app's agreed CVA convention is `CVA <= 0`, with `V_hat = V + CVA`; movement is `after - before`. A trader charge or charge ratio is a separately named business measure, not an implicit sign reversal. Rates results distinguish PV, par rate and fair spread with target leg/convention.

## Common error envelope

Proposed fields: `code`, `message`, `fieldErrors`, `retryable`, `operationId`, `detailsRef`. Useful codes include `ValidationFailed`, `ContextChanged`, `SourceVersionUnavailable`, `UnsupportedProduct`, `UnsupportedOption`, `ProviderUnavailable`, `PermissionDenied`, `IdempotencyConflict` and `ExecutionOutcomeUnknown`.

Do not put raw company credentials, connection strings or unfiltered engine dumps in end-user errors. Authorized diagnostic artifacts may contain detailed engine messages.

## Versioning

Pin Capability contract, Workflow definition, View definition, provider/engine configuration and source data revisions per execution. Additive schema changes need compatibility tests; changed financial meaning requires a new semantic version or explicit migration. Existing Runs are not edited in place when adapters change.

## Files versus production compatibility

The JSON Schemas verify shape and limited enumerations. Cross-reference resolution, catalog compatibility, B/A case construction, authorization, curve/CSA compatibility and economic semantics require additional validators. `storage.sql` is an illustrative local persistence starting point. No example claims to reproduce company ZIP/CSV/XML formats.
